# DMZ Audit 15: Final Report

**Date:** 2026-09-15

This audit is adversarial. It covers the stable DMZ contracts in the read-only `wt-main` worktree (`contracts/pool.bas`, `launch.bas`, `founders.bas`, `factory.bas`, `nfa.bas`, `nft.bas`, `chat.bas`, `social.bas`) and the new `rate.bas` from the `wt-g` worktree. It follows each contract into the code that drives it: `app/*.js`, `tools/treasurybot`, `tools/verifydeploy` and `tools/simrpc`. The audit ran as workflow `dmz-contract-audit` (wf_bad85d98-8fe). Each round had eleven finder agents: one per contract, one on cross-contract economics and fee routing, and one on the seam between the app and the contracts. All eleven worked under the DVM-BASIC rules and against the 2026-09-10 findings. A dedup agent then dropped repeats of anything already seen. Each new finding went to three verifiers, each with a different lens: REPRODUCE, REFUTE and IMPACT. A finding is confirmed when at least two of its three verdicts say it is real. Its severity is the verifiers' consensus, and a severity the verifiers changed is marked "(filed X)". The three rounds produced 26, 14 and 13 candidates, of which 22, 14 and 12 were new. That is 48 findings verified and **44 confirmed of 48**. The loop stopped at its three-round cap **without reaching two dry rounds in a row**: every round still turned up new findings. Coverage may therefore be incomplete, and another round should be run.

**Conventions**
- Contract lines are file lines unless marked "label", which means a DVM BASIC line label.
- "DVM test" means the `tests/harness` suite.
- An off-chain fix cannot be proven by a DVM test. For those findings the regression test named is the off-chain one (`tests/js`, the treasurybot Go tests, or the verifydeploy Go tests), with a DVM fixture or pin wherever chain state matters.

## Fixes that cover several findings

1. **Treasury bot.** One set of changes addresses AUD-15-02, -08, -09, -10, -11 and -21:
   - Verify every registry entry by code hash, stored treasury and template kind before reading any key.
   - Never `log.Fatal` on bad per-market data or on a refused deposit. Release the lock on every exit path.
   - Count claims from a persisted last-seen `fc`.
   - Close a deposit only on evidence that the bot's own transaction executed.
2. **Value attached at install.** Refuse DERO at install in every template, as rate.bas and founders.bas already do. This covers AUD-15-27, -39, -40 and -41, and also pool, launch, htlc, swap, vault, nfa and board.
3. **Stray value on calls that commit.** AUD-15-24, -25 and -26 need the same guard added to the entrypoints named in each finding.
4. **Length checks.** Check byte lengths with `TextEncoder` in the app before signing (AUD-15-35, -43, -44).
5. **Names and tickers.** Reserve DERO, and never label a token or author from a string its creator chose (AUD-15-05, -07, -17, -22).

## High

### AUD-15-01 · High · A front-run of a pool's first AddLiquidity sets the price, and min_lp cannot notice
**Location:** `contracts/pool.bas` AddLiquidity (file 48–104; labels 130, 140–210, 300–450, 500); `app/sheets.js:59,67,82`; `app/amm.js:32,92`; `app/forms.js:96`
**Votes:** 3/3

**Issue.** The caller's only bound in AddLiquidity is `min_lp` (label 500).
- The branch (first deposit or proportional) is chosen from the live `lp` when the call executes (label 130), not when it was signed.
- Any first deposit stores `rd = lp = d` (labels 170/190). A later depositor therefore gets `ld = muldiv(d, lp, rd) = d` exactly.
- When the quote side binds, `l = d`, which is always at least the app's `min_lp = minOut(d − 1000, slip)`. The deposit enters at whatever ratio is on chain; nothing bounds it.
- Creating a pool takes three separate public transactions: install, RegisterPool, then AddLiquidity (forms.js:96). A transaction built at `lp == 0` stays valid for about 10 blocks.
- sheets.js:82 promises "your two amounts set the opening price", which the contract does not guarantee.

**Exploit.** fee 50, pfee 5000.
1. The victim signs `AddLiquidity(min_lp = 98,999,010)` with d = 1e8 (1,000 DERO) and a = 1e9.
2. The attacker's `AddLiquidity(d = 100,000, a = 1, min_lp = 0)` executes first. The pool stores rd = 1e5, ra = 1, lp = 1e5, and the attacker holds 99,000 LP.
3. The victim's call executes at label 300: ld = 1e8, la = 1e14, so l = 1e8. It needs 1,000 asset units and refunds 999,999,000. Label 500 passes.
4. The pool is now rd = 100,100,000, ra = 1,001.
5. The attacker calls `SwapAssetForDero(1,000,000)` and receives 99,999,397 (≈999.99 DERO).
6. The victim's 1e8 LP now redeem 100,502 quote plus 997,503 asset.

The opposite direction (making the asset cheap) reverts at label 500, so only the direction that harms the victim passes.

**Impact.**
- About 999 of the victim's 1,000 DERO are taken for roughly 1 DERO plus 1e6 asset units (about 1 DERO at the victim's own price). The loss scales with the first deposit, which is usually a pool's largest.
- An honest race between two first depositors gives the same result with no attacker.
- The app exposes only DERO-quoted pools, because `canAdd = !s.quote` (sheets.js:59). The contract itself is equally exposed on wXMR and wZEC quotes.

**Fix.**
- Contract (new template hash and a redeploy): `AddLiquidity(min_lp, min_d, min_a)`, reverting after the refund computation when the d or a actually used is below `min_d` or `min_a`. Alternatively add a `first` flag: first = 1 reverts unless lp == 0, and first = 0 reverts when lp == 0.
- App, safe now: when lp == 0, send only the minimum first deposit (100,000 quote units plus the matching asset). Wait for it to be included, then add the rest as a proportional deposit, where min_lp does bound the ratio. Replace the sheets.js:82 text.

**Regression test.** DVM, `tests/pool_test.go` TestPoolFirstDepositFrontRun.
- Set up: install pool.bas (DERO quote, fee 50, pfee 5000). The attacker calls AddLiquidity(1e5, 1, 0). The victim calls AddLiquidity with d = 1e8, a = 1e9 and the new bound (min_a = 0.99e9, or first = 1).
- Assert: the victim's call returns 1, the victim's DERO and asset are refunded in full, and rd = 1e5, ra = 1, lp = 1e5 are unchanged.
- Controls: the same call on an empty pool succeeds with rd = 1e8, ra = 1e9. A proportional deposit at the on-chain ratio with min_a met succeeds.

**Status (2026-11-09)** **repaired in the source, not yet deployed.** `AddLiquidity` now takes `min_quote` and `min_asset` as well as `min_lp` and returns 1 when either amount **actually used**, after the refund computation, falls below its bound (both branches: `contracts/pool.bas` labels 155 and 475). The first deposit is checked before it stores `rd`/`ra`/`lp`, so the ratio a call enters at is the one it was signed for. `reference/pool.go` mirrors the new signature and check, `tests/pool_test.go` `TestPoolFirstDepositFrontRun` sets the exploit up (attacker seeds 100,000 : 1, then the victim's 1e8 : 1e9 deposit under the audit's numbers) and asserts the call is refused, both inputs refunded and the seeded reserves unchanged. `app/sheets.js` sends `minOut` bounds for both amounts at the user's slippage setting, and sends `min_lp` alone to a pool whose code is an earlier template (immutable, old signature), where the sheet says in the first-deposit warning that the amounts are not bounded. The template hash moved, so `app/config.js` and `deploy/networks.json` (simulator and testnet) carry the new `pool` sha256 and keep `304ca766…` as legacy. **Still required:** the DVM suite run on the new source, a simulator pass and a redeploy; the app cannot retrofit the bound into pools already installed.

### AUD-15-02 · High · The treasury bot trusts fc/fd/fa from any registry entry, so the treasury's DERO can be drained into the pass
**Location:** `tools/treasurybot/main.go:206-248`; `journal.go:166-169, 193-205, 252-278, 284-310`; `chain.go:28-42`; `payowed.go:73`; `contracts/factory.bas:71-77`; `contracts/founders.bas:201-218`
**Votes:** 3/3

**Issue.**
- `sweep()` takes every 64-character pool_/launch_ entry from the permissionless factory (anyone can register any 32 bytes for regfee) and trusts its storage.
- The only filter is `Legs()`/`isID`. There is no code-hash or treasury check: templates are checked only for NFAs (payowed.go:73), and the pool/launch hashes in config.js:26,29 are never read.
- `claimedUnits` returns `end − Before` once the growth reaches fd. It has no upper bound and is never compared with what the wallet received. `claimMarket` also credits the `fa` it read (journal.go:277).
- `Owed += units` is unchecked uint64 arithmetic.
- `depositShare` pays `shareOf(Owed)` out of the treasury wallet into founders.bas `Deposit`, which accepts anyone's deposit while hst > 0.

**Exploit.**
1. Install a contract X that stores `asset` (any 32 bytes), fd = 5000, fa = 0, fc = 0. Its `ClaimFees()` does `STORE("fc", LOAD("fc") + N)` and sends nothing.
2. Call `RegisterPool(X)` with 10,000 atomic units (0.1 DERO).
3. Hold k of hst registered pass units. Registering just before the sweep is enough (FEE-07).
4. On the next sweep, `claimable(5000, 0)` holds, fc grows by N, and `Owed[DERO] += N`.
5. The bot deposits `shareOf(N)` DERO from the treasury wallet (all of N at the mainnet share of 10000). The attacker Claims k/hst of it.
6. X never zeroes fd, so this repeats every sweep (60 s by default).

**Impact.**
- The treasury's whole DERO balance moves into the pass in 60-second steps: registration, mint, chat, rate and NFA protocol fees, plus any float. The attacker takes k/hst of it, and the bot pays the gas.
- Variant: N larger than the wallet balance makes `Must` call `log.Fatal`. On every start, reconcile resends the saved deposit and dies again, a permanent crash loop that also leaves the `.lock` file behind.
- Variant: N = 2^64 − Owed wraps the real owed amount to 0.
- No user deposits or pool liquidity are exposed.

**Fix.**
- Sweep only markets whose code hash equals the shipped pool or launch template and whose stored treasury is the bot's own address, which is the app's rule. Skip and log everything else.
- Credit `min(fc growth, fd read)` and cross-check it against the wallet's balance change in that asset.
- Use checked addition in `journal.add` and refuse to continue on overflow.

**Regression test.**
- Go (`tools/treasurybot`): a fakeChain registry with pool_0 = a forged id (code hash not a template), fd = 5000, and fc growing by 1e12 on SendClaim. Assert: no SendClaim, Owed empty, no SendDeposit.
- Go: a template market whose fc grows by 3 × fd. Assert: the credit equals fd.
- Go: Owed near 2^64 plus new units. Assert: an error, no wrap.
- Simulator: install X, `RegisterPool(X)`, run one sweep. Assert: founders `ad_0` and the treasury's DERO balance are unchanged.

## Medium

**Status (2026-11-09)** **repaired in the source, not yet run against a chain.** `tools/treasurybot/markets.go` gates every registry entry before any fee key is read: the code must hash to `templates.pool` or `templates.launch` from `app/config.js` — current or legacy, for the list the entry was registered under — and the market's stored `treasury` must be this bot's own wallet in the `ADDRESS_STRING` spelling. Everything else is skipped and named, and a build that names no template sweeps nothing. A forged entry therefore never reaches `Fees`/`FC`, which is this finding's whole exploit. The same change closes three of its neighbours: **AUD-15-09** (a missing `fd`/`fa` now reads as 0 instead of `log.Fatal`, `chain.go`), **AUD-15-10** (kind comes from the template set for the list, so a pool registered as a launch is refused rather than booked), and **AUD-15-11** (a refused or unproven deposit is logged and its record kept; `settleDeposits`/`depositShare` join errors so one asset no longer ends the process or blocks the others). `journal.add` is checked, so a credit that would pass 2^64 is refused instead of wrapping. Regression tests: `TestListedMarketsRefusesWhatTheRegistryCannotVouchFor`, `TestMarketTemplatesFromConfig`, `TestOwedUnitsCannotWrap`, with the existing crash and conservation tests unchanged; `go test ./treasurybot` is green. **Still open:** AUD-15-08 (a claim made by anyone but the bot between sweeps is never credited — needs a persisted per-market last-seen `fc`) and AUD-15-21 (a deposit closed on `ad_` growth others also cause); neither can move the treasury's funds out, but both under-count. The audit's "cross-check against the wallet's balance change" is not implemented; the template and treasury gate is what makes the counter trustworthy.

### AUD-15-03 · Medium (filed High) · An overshooting public buy is spent in full on the AMM if graduation lands first
**Location:** `contracts/launch.bas` buyto labels 30, 42–59, 200–211 (label 203 is the only bound); `app/token.js:175, 205, 221-222, 237, 249-255`; `app/app.js:250, 263`
**Votes:** 3/3

**Issue.**
- When a phase-0 buy runs past the end of the curve, buyto caps `out` at `rem` and refunds `d − used` (labels 45–59, 76). Only the phase read at execution (label 30) selects that path.
- If phase is already 1, the same call jumps to label 200 and spends all of d on the AMM. The only bound is `out ≥ min_out`, which counts tokens, not quote spent.
- Public mode signs exactly this shape:
  - The sheet shows a "Refund, the curve ends here" row (token.js:175).
  - Only private mode refuses an overshoot (token.js:221-222, app.js:253).
  - Max fills the whole balance (token.js:237).
  - go() signs `minOut(rem, slip)` (token.js:249-253), and app.trade attaches the full amount (app.js:263).
- The full amount buys far more than rem on the fresh AMM, because graduation opens at the same price with 3/4 of the curve's depth. So min_out holds even after a pump.
- If graduation happens while the sheet is open, go() re-prices in phase 1 and does not redraw the sheet.

**Exploit.** G = 1,000 DERO, supply 1e9, cbps 0, fee 50, pfee 5000.
1. The curve has rem = 8e6 tokens left. Finishing it costs about 39 DERO.
2. The victim buys 100 DERO. The sheet shows 8,000,000 tokens, a refund of about 61 DERO, and a floor of 7,920,000.
3. The attacker, ordered ahead, buys about 39 DERO. Phase becomes 1.
4. The attacker then buys about 530 DERO on the AMM.
5. The victim's call fills on the AMM for about 8.0e6 tokens (at least min_out), with no refund.
6. The attacker sells for about 625.5 DERO: roughly +56.4 DERO profit (+56.8 at the best pump size, 538 DERO).

**Impact.**
- At the most contested moment of every launch, a searcher can take nearly all of an overshooting buy's refund. With Max, the whole balance above the curve cost is spent.
- The >15% impact acknowledgement does fire for large overshoots, because amm.js:70 prices impact on the full d against rem (16,522 bps in this example). It sits beside a "Refund" row, though, so the consent is not informed. Smaller overshoots need no acknowledgement at all.
- With no attacker (an honest race, or a sheet left open across graduation), the result is an unconsented full AMM fill at a fair price, not extraction.

**Fix.**
- App, now: when a quote has refund > 0, attach `amount − q.refund` in public mode as well as private.
- Or: refuse public overshoots and offer "buy the rest of the curve", prefilled with `used`.
- go(): redraw whenever the fresh quote's phase, refund or graduates flag differs from the one shown, and compare the quote spent as well as tokens received.
- Next launch template: give buyto a bound on the quote spent (a `max_in` argument, or a price-bound min_out).

**Regression test.**
- JS: a quote with refund > 0 makes app.trade attach `amount − refund`. When fresh.phase differs from the quoted phase, the sheet redraws and nothing is signed.
- DVM (`tests/launch_test.go`): run the curve to rem = 8e6. The attacker graduates the launch and buys 530 DERO. The victim sends SwapDeroForAsset with d = used and min_out = 7,920,000. Assert the DERO spent is at most `used`.
- DVM, template version: after graduation, a buy with max_in < d reverts or refunds `d − max_in`.

### AUD-15-04 · Medium · Private mode accepts deroi/detoi receive addresses, and the payment id is dropped
**Location:** `app/token.js:159, 203, 221, 255`; `app/app.js:251-256`; `app/rpc.js:46-50`; `contracts/pool.bas:144-152, 191-199, 201-215`; `contracts/launch.bas:85-93, 174-182, 184-196`; `app/nfas.js:120`; derohe `dvm_functions.go:342-356`, `rpc/address.go:102-104, 172-176`
**Votes:** 3/3

**Issue.**
- The "Receive at" field is validated with `V.isAddress` (via `canonAddress`), which accepts the dero, deto, deroi and detoi prefixes and any payload of at least 34 bytes.
- app.trade sends the raw string as `dest`. The Review row and the wallet prompt both show the full integrated address.
- The contracts pay `ADDRESS_RAW(dest)`, which is `NewAddress(k).Compressed()`. That parses the payment id and port into Arguments and then returns only the 33-byte key.
- SEND_*_TO_ADDRESS carries no payload. `refundto` sends the whole attached value to the same bare key.
- nfas.js:120 strips an NFA charity address the same way, silently.

**Exploit.**
1. A user sells privately and pastes their exchange's deroi1… deposit address. The field's placeholder, "address that is not linked to you", invites this.
2. The payout goes to the exchange hot wallet's bare key with no payment id or port.
3. The exchange cannot attribute the deposit. If the trade is refused on min_out instead, the whole deposit goes the same way.

**Impact.**
- The whole proceeds, or the whole deposit on the refund path, arrive unattributed. For a custodial recipient they are lost unless the exchange credits them by hand.
- No attacker is needed.
- Any contract payout lacks a payload (the wallet books it as a coinbase-style entry), so even a plain dero1 exchange address cannot attribute it. The integrated form only makes the failure certain.

**Fix.**
- Refuse a dest whose prefix is deroi/detoi or whose payload is longer than 34 bytes, and say why.
- Pass `V.canonAddress(dest)` as the argument, so the prompt shows the key that will actually be paid.
- Warn that exchange and custodial deposit addresses cannot attribute contract payouts.
- Apply the same refusal to the NFA charity field.

**Regression test.**
- JS: a deroi1 dest with a destination port disables the confirm button with a message, and app.trade throws before signing. A dero1 dest is passed as `canonAddress(dest)`.
- DVM pin (`tests/ringswap_test.go`): SwapAssetForDeroTo with an integrated dest credits the bare key only. This records why the app refuses.

**Status (2026-11-09)** **repaired in the app, not yet exercised end to end.** `app/rpc.js` gained `addrParts`, `payKey` and `isPayable`: `payKey` names a payee only for a plain `dero1`/`deto1` with no trailing words, and returns null for every `deroi1`/`detoi1` (which always carries a msgpack argument map, so there is always a payment id or port to lose) and for a plain hrp with extra words, which `rpc/address.go` refuses at the wallet anyway. `canonAddress` is unchanged — feeds and the store still compare bare keys, args stripped. The three places that name a contract payee now use it: `app/app.js` `app.trade` refuses with the reason and signs `payKey(dest)`; `app/token.js` disables the confirm button, replaces its label, shows an errbox under the field, refuses to price the call, and passes `payKey(dest)` so the signed argument is the key that will be paid; `app/nfas.js` `startSheet` refuses an integrated charity address and stores the canonical key. The private-mode note now says a contract payout carries no payment ID, so an exchange deposit address cannot attribute it even in its plain form. The review row and the wallet prompt follow the argument, so both now name the key actually paid.

New test `tests/js/payee.test.mjs` (registered in `tests/js/index.js`) pins it against real addresses: a plain `dero1` and a `deto1` are payable, `deroi1`/`detoi1` are refused while `canonAddress` still strips them to the same key `addressRaw` would store, and the two shapes the wallet itself rejects (integrated hrp with no arguments, plain hrp with trailing words) are refused too.
